# 0006. cron の間隔を 10 分に詰める

## 状態

有効 ([0005](./0005-cron-every-3-hours.md) を置き換える。変更検知の仕組みは
[0004](./0004-frequent-cron-with-change-check.md) のまま)

## 文脈

[0005](./0005-cron-every-3-hours.md) で cron を 3 時間ごとに広げた。理由の
一つは Actions の実行枠を空振りで消費したくないことだった。

しかしこのリポジトリは公開リポジトリで、GitHub-hosted の標準ランナーの
実行時間は課金枠 (無料分の分数) を消費しない。枠の心配が無くなると、
3 時間という反映の遅さだけが残る。

空振りの起動が軽いことは実測で確かめてある。変更が無い回は `check` ジョブ
(Cosense API への 1 リクエストと `actions/cache` の `lookup-only` 照会) が
4〜5 秒で終わり、`deploy` ジョブは `skipped` になってランナーも確保されない。

## 決定

- cron を **10 分ごと** (`3-59/10 * * * *`、毎時 03 / 13 / 23 / 33 / 43 / 53 分)
  にする。毎時 0 分は GitHub 全体で混み合い遅延・取りこぼしが出やすいので
  3 分にずらす (0004 と同じ理由)
- `check` ジョブによる変更検知・指紋の記録・手動実行の扱いは 0004 のまま変えない

### 却下した案

- **3 時間のまま据え置く**: 枠の消費という理由が無くなり、反映が遅いだけになる
- **5 分ごと (cron の最短)**: GitHub の schedule は混雑時に数分〜十数分遅れる
  ため、5 分と 10 分の差は実際の反映時間にほとんど現れない。起動回数だけが倍になる
- **15 分 (0004 に戻す)**: 空振りが軽く枠も消費しない以上、反映を 5 分遅らせる理由が無い

## 影響

- 記事の反映・doctor 停止からの自動復帰が最大 10 分 (+ GitHub の schedule 遅延) になる
- 起動回数は 1 日 8 回から 144 回に増える。ほとんどは数秒で終わる空振りで、
  Actions の実行履歴は 0005 の文脈で挙げたように埋まりやすくなる。履歴の
  見通しより反映の速さを優先する
- リポジトリを private に戻すと空振りの起動も課金枠を消費する。その場合は
  間隔を見直す
- 1 日 1 回は必ず公開まで走る挙動 (指紋に UTC の日付を含める) は変わらないので、
  稼働記録コミット ([0003](./0003-heartbeat-commit-keeps-cron-alive.md)) による
  cron の維持にも影響しない
